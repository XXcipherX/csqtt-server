# Архитектура сервера 2.5.0

CSQTT собирается в один Rust-бинарник `csqtt`. Один процесс запускает сетевой протокол, пакетный dataplane, хранение состояния и встроенную веб-панель. Для сборки используются Rust 1.97.1 и edition 2024.

## Транспорт и протокол

`protocol.rs` обрабатывает регистрацию клиентских потоков, аутентификацию, control messages, UDP-трафик и передачу IP-пакетов в TUN. Лимит потоков — 100; сессии, каналы управления и служебные таблицы имеют отдельные ограничения.

`shared/dtls.rs` содержит DTLS 1.2 handshake, сертификаты, проверку fingerprint, защиту DTLS records и выработку ключей SRTP. Серверный протокол различает DTLS и RTP/SRTP-пакеты на одном UDP listener.

`shared/wire_protocol.rs` задаёт фрагментацию: magic `0xCF`, 8-байтовый заголовок, до 1272 байт полезной нагрузки в одном фрагменте и до 2048 байт в восстановленном пакете. Reassembler учитывает отправителя, идентификатор пакета и тайм-аут; отдельный модуль `path_probe.rs` отвечает за сообщения проверки сетевого пути.

В этой версии используются `GETCONF` без обязательного device ID и суффикса ревизии и ответы `TUNCONF` с `stream-v1`. При этом служебная команда `--protocol-revision` сохраняет значение `CSQTT-WIRE-3` из `main.rs`.

## Dataplane

`dataplane.rs` запускает отдельный поток с Tokio `current_thread` runtime. `tokio_io.rs` отвечает за UDP- и TUN-ввод-вывод; протокольная логика вызывается через `DataplaneLogic` и `PacketOutput`.

В Linux используются readiness notifications, `recvmmsg` и `sendmmsg`, пакетная обработка и ограниченные буферы. Цикл чередует приоритет UDP и TUN, принимает команды через ограниченный `tokio::sync::mpsc` и выполняет обслуживание по таймеру. `packet.rs` содержит пакетные буферы и разбор IP-заголовков.

После ошибки уже запущенного dataplane внутренний supervisor пересоздаёт его с задержкой от 1 до 30 секунд. Ошибка первого запуска и окончательная остановка передаются в основной runtime. Основной процесс отслеживает также задачу веб-сервера и выполняет завершение при фатальной остановке одного из компонентов.

`tun_device.rs` содержит таблицу маршрутов и распределение трафика между потоками. TUN-интерфейс по умолчанию — `csqtt1`, адрес сервера — `10.66.67.1`, IPv4-подсеть клиентов — `10.66.67.0/24`.

## Состояние и маршрутизация

`model.rs` описывает конфигурацию, пароли, группы клиентов, правила маршрутизации и local proxy profiles. Состояние сохраняется в SQLite (`csqtt.db`) в каталоге конфигурации; запись снимков вынесена в отдельный поток `csqtt-db-writer`. При загрузке предусмотрено обновление схемы базы.

`proxy_route.rs` и `tproxy.rs` реализуют серверную часть локальных proxy profiles и перенаправления трафика. Эти настройки сохраняются вместе с остальной конфигурацией и доступны через панель.

## Веб-панель

`web_panel.rs` содержит HTTP API, HTML, PWA manifest и статические ресурсы. Список доменов из `app/src/main/assets/domains.txt` встраивается при компиляции. Панель предоставляет управление клиентами и группами, правилами маршрутизации, DNS, proxy profiles, статистикой и журналами.

HTTP и HTTPS обслуживаются на одном настраиваемом порту, по умолчанию `46002`. TLS-сертификат и ключ находятся в постоянном каталоге конфигурации. Для панели доступны переменные окружения с логином, паролем, префиксом пути и настройкой secure cookie.

## Контейнер и сборка

Dockerfile выполняет двухэтапную сборку. Builder использует Rust 1.97.1 и Debian Trixie, а release-бинарник собирается под native target каждой платформы. Runtime-образ запускает `/usr/local/bin/csqtt` и содержит сетевые утилиты, необходимые серверу.

`.dockerignore` ограничивает контекст сборки Cargo.toml, Cargo.lock, Rust-модулями и списком доменов для панели. Настройка musl target из `.cargo/config.toml` применяется при сборке через Cargo; Dockerfile явно выбирает GNU target builder-контейнера.

Контейнер требует host networking, `/dev/net/tun`, capabilities `NET_ADMIN` и `NET_RAW`, IPv4 forwarding и подходящие NAT/firewall rules на VPS. Постоянные данные подключаются к `/etc/csqtt`. Инструкции по сборке и запуску приведены в [README.md](README.md).

GitHub Actions выполняют серверные проверки, upstream-контракт 2.5.0 и сборку Docker images для AMD64 и ARM64. Публикация образов вынесена в отдельный workflow с запуском вручную или по тегу `v2.5.*`. Проверки также можно запустить вручную в подготовленной среде.
